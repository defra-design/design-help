How Design help has been built

This page explains how we built Design help in practice. It covers the tools we used, where it runs, what we changed for Defra, and how we used AI to help write the code. We wrote it so people who use or look after the tool can see how it was made. It is not a formal document for buying or auditing the service.

How we used Cursor and AI to write the code

We used AI-supported development for almost all of the coding. Most of that work happened in the Cursor editor. We used agent-style flows: you describe the task in plain language, the tool can change several files at once, and it can suggest commands. A person still checks the result in the browser and decides what to keep.

The maintainer is not a full-time developer. This way of working meant we could cover more in less time than we would expect from one person working only by hand.

The work was iterative and conversational. Some people call that informally “vibe coding”. The maintainer set the direction, tested what changed, and chose what to merge.

This approach is not the same as a full delivery team with strong checks for a high-scale public service. It is a deliberate test of how far we can get with modern AI tools when the audience is smaller and the risks are clearer.

GOV.UK Prototype Kit and accessibility

We built the service with the GOV.UK Prototype Kit. That includes GOV.UK Frontend and patterns people already know from GOV.UK services. We used prompts and project rules to ask the AI to follow Kit guidance and documented components unless there was a good reason not to.

Accessibility matters. We want journeys to be clear and easy to use, including for people who use assistive technology. The kit does not by itself prove we meet every WCAG success criterion. It does give a solid starting point: sensible page structure, typography, visible focus, and many components that are built with accessibility in mind.

We kept Defra-specific styling light so we were less likely to weaken that starting point by accident.

Defra branding and layout

This version of the service is Defra-only in its look and wording. We changed the default kit header, built a custom footer, and adjusted the navigation strip, favicon, and colours. These are presentation changes. We tried to stay close to familiar GOV.UK behaviour and patterns.

Where it runs

The live app runs on Heroku. We store data in a PostgreSQL database in the same environment. Sign-in and sessions need that database to be running and set up correctly.

Security

We have not run strong, independent security testing on the tool. For example we have not had a penetration test or a full threat-model exercise. We rely on sensible defaults from the kit, PostgreSQL, and Heroku, and on being careful about what data we hold.

For how the service is used today, we think the security risk is relatively low. It supports an internal design community, the audience is limited, and it does less than a live government transaction service. We should review that view if more people use it, if we hold more sensitive data, or if we add new systems that connect to it. If the role of the service grows, we would expect more testing and clearer governance, and we might need to change how it is built.

Working in the open about this build

Part of building this way was an experiment. We wanted to see if we could ship something useful quickly with AI help and a clear brief from a person. Similar work might once have needed several people over several weeks.

There are trade-offs: you can move fast, but you may do less deep review. You can explore ideas, but you may be less consistent than a larger team. Working in the open about those trade-offs helps us judge when this way of working is good enough — and when we need a different approach.
